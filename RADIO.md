# PLAN — Pilgrim Dot Farm Radio (rev 2)

An AI-generated radio station. A single **PLAY** button starts continuous,
gap-free audio: songs generated by MiniMax Music 3, plus news, commercials,
DJ talk, and station liners written by LLMs and voiced by Kokoro TTS.
Nothing is wasted: finished songs and evergreen spots are recycled.

**Slogan:** *Pilgrim Dot Farm*

---

## 0. Core principles

1. **Playout never waits on production.** Everything that airs is fully
   rendered, checked, and normalized before it enters the program. Generation
   latency is absorbed by inventory and lookahead, never heard by the listener.
2. **Production is demand-driven, not clock-driven.** Producers refill
   inventory whenever stock falls below a target. The M5 generates songs
   continuously.
3. **Seamlessness is a client concern.** The browser schedules decoded audio
   sample-accurately with the Web Audio API. No `<audio>` element handoffs.
4. **Everything is testable with fakes and a simulated clock.** A full day of
   station operation must be simulatable in seconds.

---

## 1. Scope

**Phase 1 (this build):** random segment selection, inventory-based
production, song and voice pipelines, QC and loudness normalization, cold-start
seeding, simulation tests, minimal UI (PLAY/STOP + streaming indicator).

**Deferred:** the hour clock with hard :00/:30 news posts (Phase 2). The
segment selector is an interface so the clock can replace random selection
without touching the rest of the system.

## 3. Architecture overview

```
                 ┌─────────────── PRODUCERS (background, demand-driven) ───────────────┐
                 │                                                                      │
 config.yaml ──▶ │  song pipeline:  brief (qwen38) ─▶ MiniMax (M5) ─▶ QC ─▶ normalize   │
                 │  voice pipeline: copy (qwen38/ornith) ─▶ TTS cleanup ─▶ Kokoro        │──▶ library/ + station.db
                 │                  ─▶ QC ─▶ normalize                                   │     (inventory + ledger)
                 └──────────────────────────────────────────────────────────────────────┘
                                                   │
                                                   ▼
                 ┌─────────────── PLAYOUT (scheduler.py) ──────────────────────────────┐
                 │  selector.choose_next()  ─▶ planned items ─▶ contextual items        │
                 │  rendered just in time ─▶ COMMITTED program (≥5 min ahead)           │
                 └──────────────────────────────────────────────────────────────────────┘
   library/*.mp3 ─▶ media publisher (background) ─▶ S3 public bucket ─▶ CloudFront (§8.4)
                                                   │  GET /api/station/program
                                                   ▼
                 ┌─────────────── CLIENT (browser) ────────────────────────────────────┐
                 │  fetch(url: CloudFront) ─▶ decodeAudioData ─▶ .start(when)           │
                 │  heartbeat {seq, position} ─▶ server (airplay + listener count)  │
                 └──────────────────────────────────────────────────────────────────────┘
```

Program model: a **sequence** of items with sequence numbers, not wall-clock
timestamps. Phase 1 assumes a single listener. The playhead runs on the
**origin's clock** (`scheduler.py`), not on any client report: the scheduler
keeps the committed window full relative to that clock. Heartbeats
(`POST /api/station/heartbeat`, every 5 s per playing browser) feed the live
listener count and the `airplay` ledger; they do **not** drive the playhead.
Wall-clock alignment only matters once the hour clock arrives.

*(Doc correction, SPLIT_PLAN §1.6: an earlier version of this section claimed
the client reports its playhead via heartbeat and the scheduler follows it.
That was never true in the code — see `scheduler.py`'s committed-window clock.)*

Programme identity and manual control (TUI.md): the station carries an
**`epoch`** (changes on restart) and a programme **`revision`** (changes only
when already-published future playback changes). A Textual **DJ console** (see
`pilgrim/tui/`, §18) controls this same **shared** timeline over HTTP; the
browser stays the only audio engine (§9.2). Public request-line behaviour is
unchanged and separate from privileged DJ mutations (§11).

**Idle and wake (IDLE.md).** The playhead runs on the origin clock, so with
nobody listening it would burn through one-shot inventory and keep the
producers working for an empty room. With `idle.enabled` (default), when no
player has heartbeated for `idle.after_s` the scheduler **freezes**: the
already-rendered committed window (≤ `committed_lookahead_s`) stays exactly
as it is, production pauses (listener requests excepted, §6.1), and `on_air`
stays true (the window is still playable, so PLAY is never disabled). The
first `GET /api/station/program` (PLAY) or heartbeat **thaws** it
synchronously: the playhead resumes where it stopped, stale time-bound future
rows are dropped, song-after-song gaps are bridged with words, the revision
bumps, and the same response returns a full playable window. `/api/health`,
`/api/station/state`, `/api/requests`, `/api/visitors` and media never wake it
(idle pages, bots and smoke checks poll those). `idle.enabled: false` restores
the always-running behaviour exactly.

## 4. Content types

Content falls into three production classes. This split determines when each
item is made.

| Class | Types | When produced | Recyclable |
|-------|-------|---------------|-----------|
| **Evergreen** | songs, commercials, generic liners, station IDs, promos, named song intros | Well ahead, into inventory | Yes |
| **Expiring** | news bulletins, clock reads, day-level promos | On a refresh cycle; carries `expires_at` | Never |
| **Contextual** | DJ talk-ups (back-announce), field reports | Just in time, once neighbors are known | Never |

Segment types the selector chooses from:
- `song` — one song (fresh preferred over recycled).
- `commercial_break` — 1–2 commercials, optionally closed by a liner.
- `liner` — short station ID or gag line; `meta.kind` ∈ `station_id | gag |
  weather | town_notice | promo` (weather/town_notice are optional extras).
- `dj_talk` — contextual talk-up about recent songs, the day, the town and a
  rotated topic. **Time-free**: the clock is carried by `time_check` only.
- `time_check` — a 3–5 s clock read, **code-written** (no LLM), airing at
  :00/:15/:30/:45 (ANNOUNCER §A4).
- `promo` — a 10–20 s station promo; `meta.kind` ∈
  `campaign | request_line | paid_tier | tree_fiddy`.
  Campaign promos are LLM-written with code-filled day tokens and expire at
  local midnight. Request-line, paid-tier and Tree Fiddy Report promos are
  code-written config lines (no LLM). The Tree Fiddy Report is voiced by the
  operator character (Jimmany, `am_justin`), carries the real count of paid
  requests aired in the last 7 days, and is regenerated hourly. Paid-tier
  promotion is **copy only**: no payment code ever runs in playout (AGENTS
  rule 11), and it never names a buyer or email.
- `intro` — the named song intro; **evergreen** (recycled with its song), except
  a listener-request intro, which is one-shot.
- `news` — the current bulletin, if one is valid.
- `field_report` — the British field reporter, filing invented farm factoids
  from a literal field; always closes with his "outstanding in my field"
  sign-off (enforced in code). Contextual: aired once, never recycled.
- `operator_phrase` — a phrase submitted **verbatim** by the station operator
  through the DJ console (TUI.md §6): the typed words are the copy, never
  rewritten or extended by an LLM. One deterministic exception: if the message
  does not already open with the administrator sign-on (`dj.phrase_prefix`,
  default `"This is the administrator,"`), the server prepends it so listeners
  know who is speaking; matching ignores case and trailing punctuation, and the
  prefix counts toward `phrase_max_chars`. The cleaned, hashed text includes
  the sign-on. Rendered once by the operator's character
  (§10) with the mandatory TTS cleanup (§6.3). One-shot (never recycled);
  counts as a voice bridge and non-song segment with DJ-like news adjacency
  (§5.2); no automatic SFX in v1. Not drawn by the selector — only ever
  scheduled by "Queue phrase"

**SFX** (`sfx` items, SFX.md): short sound effects rendered by the MOSS-SoundEffect
v2.0 backend. They are **never airable on their own**: they ride on a host clip
(`dj_talk`, `field_report`, `commercial`, `liner`) as sidecar overlays recorded
in the host's `meta.sfx` as `{item_id, cue, kind, offset_s, duration_s}`,
`kind` ∈ `stinger | joke | bed`. **News never carries SFX**, by construction.
Cues are curated by ear in `sfx.cues`; only `approved` ones render or air.
Evergreen cues (fixed seed) form a small recycled stock pool; contextual cues
(e.g. barnyard animals, the field reporter's wind bed) are rendered fresh for
the clip that calls for them. Scripts ask for cues by sentence
(`"sfx": [{"cue", "after_sentence"}]`, `"joke_after_sentence"`); the offset is
a coarse word-share estimate of that sentence boundary — an intentional beat,
not syllable accuracy.

## 5. Playout — `scheduler.py`

### 5.1 Selector interface

```python
class Selector(Protocol):
    def choose_next(self, state: PlayoutState) -> SegmentType: ...
```

Phase 1 ships `RandomSelector`. Phase 2 adds `ClockSelector`. Selectors are
pure functions of state plus an injected RNG, so tests are deterministic with a
seed.

### 5.2 RandomSelector rules

Weighted random choice, **restricted to segment types that have ready
inventory**. If the drawn type is unavailable, re-draw from the available
types. Default weights (tunable in config):

| Segment | Weight |
|---------|--------|
| song | 0.55 |
| dj_talk | 0.12 |
| commercial_break | 0.15 |
| liner | 0.10 |
| news | 0.08 |
| field_report | 0.05 |
| promo | 0.05 |
| time_check | 0.04 |

Weights are **per-item draw probabilities, not airtime shares** (a 110 s song
and a 5 s liner are drawn, not timed). The realized non-song share is bounded
by `max_consecutive_non_song`: with 2 slots it cannot exceed
`2 × mean_non_song / (mean_song + 2 × mean_non_song)` (21.7% at the measured
110.3 s / 15.3 s averages). Do not configure weights that assume otherwise;
`playout.hour_budget` is the explicit mix knob (ANNOUNCER B0).

Constraints (applied before drawing):
- At most **2 consecutive non-song segments**; after that, force `song`.
- `news` at most once per **20 min** of program time.
- A news bulletin never airs after its `expires_at` (default 45 min after
  creation).
- If the last bulletin is tagged `serious`, the next non-song segment may not
  be a `commercial_break` (avoids satire landing on real tragedy).
- Same commercial: minimum **30 min** separation.
- Same song: minimum **4 h** separation, relaxed stepwise (4 h → 2 h → 1 h)
  only when the pool is too small to satisfy it. (The config ships
  `[3600, 1800, 900]`, a 1 h → 30 m → 15 m relaxation; the exact rule is open
  question Q1 in PRIORITIES.md.)
- Genre: no genre repeated within the last **3** songs.
- **Song priority (PRIORITIES §2 tier table):**

  | Tier | What | Rule |
  |------|------|------|
  | 0 | Ready listener-request song | Jumps the line (unchanged, 4.7). |
  | 1 | Fresh (never-aired) song | **Newest first** (LIFO); airs at the next song slot. |
  | 2 | Recycled song | **Weighted random** over songs that clear spacing. |

  **Starvation guard:** an aired song whose wait reaches
  `song_rotation.starvation_h` (6 h) minus `starvation_margin_s` (600 s) is
  picked outright, longest wait first, so weighting can never make a song
  disappear. Tier-2 weight is `youth * (wait_floor + (1 - wait_floor) * wait)`
  (`playout.song_rotation`, §12): **youth** halves every `half_life_h` hours
  (floored at `youth_floor` so no song starves); **wait** grows 0..1 while a
  song goes unheard, saturating at `wait_target_h` (a never-aired song counts
  as unheard forever). Recent songs lean up; old songs thin out, they don't
  disappear. Weighting never breaks spacing — it only orders songs that
  already pass it. Spacing and the wait factor read the persisted
  `last_aired_at` wall clock, not an in-memory air map, so a restart keeps the
  rotation instead of re-airing the oldest song first.
  **Ratings (VOTING.md Step 8, off by default):** when
  `ratings.rotation_weight` is true, a song with at least
  `rotation_min_votes` ratings has its tier-2 weight multiplied by
  `clamp(avg / 3, 0.25, 1.5)` — a 3-turkey song is neutral, a 5-turkey song
  gets half again. It is a store read only (no time/random), never breaks
  spacing and never overrides the starvation guard. The shipped config has it
  off.
- **Words between songs.** Every pair of songs has at least one voice item
  between them: a `liner` / station ID, `dj_talk`, a `field_report`, or the
  next song's own `intro`. Commercials and news alone don't count. While no
  voice item has aired since the last song, the selector spends the last
  non-song slot (before `max_consecutive_non_song` forces a song) on a
  callout, and a commercial break leaves that slot free. If a song is still
  about to follow bare, the scheduler puts a liner or station ID in front of
  it (repeats allowed), then the emergency station IDs (§8.3). Never waits:
  with no voice item at all, the song airs.
- **Loose time awareness.** When the next slot airs within
  `playout.top_of_hour_window_s` of :00 (wall clock), a pending callout is
  drawn first and DJ talk (which carries the time) is favored. A nudge, not a
  hard top-of-hour ID.
- Song spacing and `last_aired_at` use the song's scheduled **air** time
  (now + committed coverage), not its commit time.
- **Manual DJ queue (TUI.md §5).** Songs and operator phrases queued from the
  DJ console are manual and FIFO — they go **ahead of** automatic selection, in
  submission order, but still clear spacing, gravity, the maximum non-song run,
  news expiry/adjacency, the words-between-songs rule and all other §5.2
  constraints against the **new** timeline. v1 has no implicit repeat override;
  an ineligible selection is shown with the reason. Ready listener requests
  keep their relative order behind the manual queue.
- `dj_talk` never adjacent to another `dj_talk` or to `news` (either order).
- `field_report` never adjacent to `news` (either order) or to another
  `field_report`, and is held back after a `serious` bulletin like a
  `commercial_break`.
- `promo` never adjacent to `dj_talk` or another `promo`, and is held back after
  a `serious` bulletin. A campaign under its `per_hour` target triples the
  promo weight (soft nudge; never forced past a constraint). Each promo kind
  has its own spacing: campaign/global `promo_min_spacing_s` (600),
  `request_line_gap_s` (2,700), `paid_tier_gap_s` (1,800) and
  `tree_fiddy_gap_s` (3,600). The most overdue due kind wins.
- `time_check` never adjacent to `dj_talk`, `news`, or another `time_check`.
  It is **due** only when the next slot airs within
  `talk.time_check_window_s` of a configured mark (`time_check_marks_min`,
  default :00/:15/:30/:45) and the last check is at least
  `talk.time_check_min_gap_s` old. When due it is **committed** (a
  commitment, not a nudge), unless it would break the non-song run limit.
  The variant aired is the one rendered for the slot's own 5-minute bucket, so
  the spoken time is never more than the rounding off.
- Same liner: not replayed within `liners.repeat_gap_items` committed items
  (20) or `liners.repeat_gap_s` wall seconds (2,700).
- **SFX at commit time** (`sfx_plan.py`, pure over the injected RNG): only
  the SFX host types carry overlays (never news); a `joke` overlay (the
  rimshot) airs on a coin flip (`sfx.joke_p`, 50/50); a stinger that would run
  past its host's end is dropped (never push a join); at most
  `sfx.max_per_window` (3) stingers start in any `sfx.window_s` (10 s) of air.
  Beds are ambience and don't count. A missing or retired sfx item is skipped;
  the host still airs.
- `liner` never follows a `liner` while any other interjection (commercial,
  `dj_talk`, news) is ready, and the same liner isn't replayed within the last
  10 committed items. With no songs ready, the station fills with commercial
  breaks, DJ talk and news; liners stay bridges, not the program.
  A liner or commercial may break its own spacing only to bridge imminent
  dead air (committed coverage below `playout.filler_horizon_s`); the
  lookahead is never padded with repeats, so fresh items reach air within
  about that horizon instead of queuing behind minutes of the same liner.
- **New songs air as soon as they are made.** When no song is airable, the
  scheduler commits interjections only up to `playout.filler_horizon_s` ahead
  (enough to avoid dead air), never a full lookahead of spots or talk. A song
  that lands mid-drought takes the next open slot, within about that horizon.
  Among waiting fresh songs the newest airs first (LIFO, PRIORITIES §2).
  The ≥5 min committed lookahead (§5.3) holds only while songs are airable.
- **Listener-request songs jump the line** (OVERHAUL 4.7): when a ready
  request song exists and a song is allowed right now (the interjection rule
  above still holds), `song` is committed. Each song airs with its short
  `intro` immediately before it; intros are consumed and never recycled, are
  treated as part of their song for all constraints. A stock intro is skipped
  if it would land right after a `dj_talk`; a **request** is never taken in
  that slot (its intro is the on-air thank-you), it takes the next song slot.
  When the song + intro are ready they are **spliced into the next song slot**
  ahead of already-committed stock songs, not appended at the tail, so the
  request airs at the next boundary instead of behind the lookahead. The splice
  renumbers future occurrences with fresh seqs (never reusing an old seq) and
  bumps the programme revision; revision-aware clients cancel their obsolete
  future sources and refetch the snapshot (TUI.md §5, §9.2). Optional hold:
  with `playout.request_hold_max_s` > 0, while a request is still
  queued/producing the committed window is held at `playout.filler_horizon_s`
  so no stock song queues ahead of it, bounded per request by that value. It
  ships **0 (off)**: holding for a request that takes minutes to write and
  render filled the air with liners (2026-11-01). With it off, songs keep
  airing and a ready request splices into the next song slot.

### 5.3 Planned vs. committed

- **Planned** items are chosen but may still need rendering (contextual items).
  Contextual talk is produced ahead into a small stock shelf, not planned at
  commit: the producer writes time-free copy, renders it, and the scheduler
  commits only already-rendered items.
- **Committed** items are fully rendered and visible to the client.
- The scheduler keeps **≥5 min of committed audio** ahead of the client
  playhead (from heartbeat) and plans a few items past that, while songs are
  airable (song droughts and pending listener requests are the exceptions: see
  §5.2 — the window is held at `filler_horizon_s` while a request renders, and
  a ready request is spliced into the next song slot with a revision bump).
- **Time-bearing audio is rendered per 5-minute bucket, and the bucket is
  chosen at commit** (ANNOUNCER §A3). The LLM writes copy once with a
  `[[clock]]` token and no clock; the producer renders one cheap variant per
  upcoming bucket (Kokoro ~0.2 s), each stamped `meta.bucket` and expiring at
  its bucket's end. At commit the scheduler knows the exact air slot
  (`_slot_wall`) and commits the variant whose bucket matches it, so the
  spoken time is never more than the rounding off. A splice, skip or prepared
  cutover bumps the revision and re-selects the variant for the new slot. A
  slot with no valid variant falls back to a liner. Nothing in the commit loop
  calls an LLM or Kokoro: playout never blocks on production.
- **Epochs, revisions and prepared cutovers (TUI.md §5).** The station `epoch`
  changes on restart; the programme `revision` changes when already-published
  future playback changes, while ordinary append-only lookahead may keep its
  revision. `GET /api/station/program?epoch=E&revision=R&after_seq=N`; on an
  E/R mismatch the server ignores the stale cursor and returns a full snapshot
  with `reset: true`, start offset and server time (§11). Sequence numbers
  identify occurrences and are never reused for a different item (§5.5). A DJ
  command is serialized with the normal commit loop, validated against
  epoch/revision/current occurrence + availability, and applied as a
  **prepared cutover** (§5.5) built only from already-rendered inventory — never
  a production call under the scheduler lock.
- **Frozen playhead (IDLE.md).** `Scheduler.freeze()` pins `position()` at its
  current value (`_frozen_at`); `commit_lookahead()` while frozen only splices
  ready listener requests and returns (no fill, no trim: the window is static,
  and consuming one-shot inventory for airtime nobody hears is waste).
  `thaw()` shifts `_offset` by the frozen span so playback resumes exactly
  where it stopped, then revalidates the committed future for the new wall
  time: every future `time_check` and every future row whose `expires_at` has
  passed for its new slot wall is dropped (`time_check` items already expire
  at their bucket's end; the explicit type check is a belt-and-braces for an
  emergency read rendered without one). Dropped one-shots are spent, not
  returned to the pool (§5.5). Where a drop leaves a song directly after a
  song, `_pick_callout_fallback()` inserts a liner/station ID (fresh seqs
  above the high-water mark, tail renumbered; §5.2). Anything dropped or
  inserted bumps the revision once; then the window is topped up from
  already-rendered inventory only. A request song can never be dropped
  (songs are evergreen) and the **on-air row is never revalidated**: a stale
  clock read that is already playing out finishes, because dropping it would
  mean dead air.

### 5.4 Fallback chain

When the selector finds nothing suitable:
1. Recycled song (longest since last aired).
2. Any evergreen commercial or liner (station IDs draw as liners).
3. **Emergency pack** (§8.3): pre-rendered, never deleted, stored on the M5.
   Emergency station IDs are also the floor for words between songs (§5.2).

Silence is never an option.

### 5.5 Manual control — skip, queue, phrases (TUI.md §5)

DJ mutations change the **shared station programme** for compatible, connected
listeners. They ride the same scheduler commit loop with stricter provenance:

- **Commands and idempotency.** Every mutation is a JSON command carrying a
  client-generated `command_id`, `expected_epoch`, `expected_revision` and,
  for skip, `expected_seq`. Commands are **idempotent by command ID + payload**:
  an identical retry returns the existing result (lost-response recovery); reuse
  with different content is `409`. Idempotency is checked **before**
  stale-state checks. Durable outcomes: `accepted → preparing → scheduled →
  applied`, with `rejected` and `expired` terminal results (§11).
- **Concurrency.** If epoch/revision/current occurrence no longer match (the
  console acted on a stale view) the command is `409` stale and the console
  refreshes its display instead of acting on it. Error taxonomy (each with a
  stable `code` and readable `detail`): 401/403 authentication/authorization,
  404 missing ID, 409 stale/ineligible/conflicting, 422 invalid input,
  429 bounded queues, 503 required service unavailable.
- **Prepared cutovers.** A validated command builds a replacement tail from
  already-rendered inventory (no production call under the lock), publishes a
  **prepared** replacement (cutover ID, target revision, media list, proposed
  effective time), then — after a bounded preparation window — atomically
  activates it at a cutover time with enough configured lead for client
  notification (§9.2). Only **one** cutover is prepared at a time; later edits
  rebase on it. The active programme stays valid while preparation is pending.
  All scheduling arithmetic uses the injected Clock/RNG (§0, §15).
- **Skip.** Skips the item identified in the displayed state (the server checks
  it is still current). An intro + its song are one selectable unit: skip
  during the intro skips both; skip during the song ends the song. A multi-spot
  commercial break skips the current spot (v1). If the current segment ends
  during preparation, the skip expires as stale instead of skipping its
  successor. The action's scope is shown before execution.
- **Queue next.** FIFO into the earliest eligible boundary after the current
  segment, showing the actual planned position and any required bridge — it must
  not silently wait behind the existing committed window. Eligibility (a ready
  song or this character's ready phrase) is revalidated at insertion time; v1
  shows a clear reason when spacing/gravity makes it ineligible, and has no
  implicit repeat override. Existing ready listener requests keep their
  relative order. **Operator phrases** are the exception to "earliest
  boundary": they are appended at the **tail of the committed window** (a
  brand-new seq, never a mid-window splice) because legacy clients merge
  fetched rows by seq only — a splice inside rows already fetched is silently
  lost, and shifted rows can double-play (TUI.md §6, §9.2). If the tail's
  predecessor is dj_talk/news/another phrase the phrase defers and retries
  next scheduler cycle. The job reaches `aired` when its row falls behind the
  playhead, and expires from any pre-air state when its TTL passes.
- **What edits preserve.** Non-song runs, spacing, gravity, news expiry/
  seriousness adjacency, genre repeats and words-between-songs are revalidated
  against the **new** timeline after compression. Unstarted intro/song blocks
  that move intact with valid context transfer their one-shot reservation (one
  planned airing); cancelled/superseded one-shots — news, DJ talk, intros,
  field reports, operator phrases — lose their reservation permanently and are
  **never** returned to the pool. Bypassed songs/requests are never marked
  heard; actual started-then-skipped airings are recorded separately from
  never-started/superseded occurrences. SFX stop with their host and the
  stinger budget is recalculated at the new start times; a sidecar is never
  aired standalone. Edits create control/history records; they never retire,
  delete or modify library media or emergency inventory.

## 6. Production — `producer.py`

### 6.1 Inventory targets (low-water marks)

The producer loop checks inventory and refills whatever is furthest below
target, per host worker.

| Item | Target |
|------|--------|
| Fresh (unaired) songs ready | ≥ 2, counting stock renders in flight (stock generation stops at `songs.stock_max_library` usable songs) |
| Song briefs queued | none: each song job writes its own brief while other jobs render (`inventory.briefs_queued` is unused) |
| Current news bulletin | 1 valid; refreshed every 30 min |
| Commercials (library) | ≥ 20 at launch; top up slowly (they repeat on purpose) |
| Liners, by length bucket (3 / 5 / 10 / 15 / 30 s) | ≥ `inventory.liners_per_bucket` each (4 → 20 total) |
| Promos | campaign: `inventory.promos_min` (4) while the ramp runs; steady kinds: 2 request-line, 2 paid-tier, 1 Tree Fiddy Report |
| Named song intros | one per song, rendered once with the song, evergreen |
| Clock reads | one variant per 5-minute bucket for the next hour (12) |
| Unaired field reports | ≥ `inventory.field_reports_min` (1) |
| Emergency station IDs | `inventory.station_ids_min` (3), rendered once, never deleted |
| Evergreen SFX stock | one per approved evergreen cue |

The voice worker fills callouts first (emergency station IDs, liners, DJ talk),
then commercials (a few per cycle) and field reports. It runs alongside the
song worker, so talk is ready by the time a new song lands.

The song worker (`Producer.song_loop`) is a decider that keeps up to
C = the generator pool's healthy slots (`songs.gen_backends`, §6.2) song jobs
in flight. Each job is brief → render → intro → store. The decider picks:
1. the next queued listener request (queue order: paid first, FIFO within a
   tier), scanning past requests that can't start yet. Up to
   `songs.free_request_slots` (2) free requests render at once.
2. otherwise a stock song.
Free requests and stock together never occupy every slot: one stays open for
a paid request. Paid jobs don't count against that, so with two paid requests
rendering a free one may take the third (with C = 1 free/stock use the slot
whenever it is idle). Paid requests may take any free slot, several at once. Ready order
is air order (the splice, §5.2), so a request song that finishes early is
**held** outside the library until every request ahead of it in queue order
that is still in flight has become ready, failed, or been re-queued. A paid
request is ahead of every free one, even one that started first. A held song
is lost on a crash; its request re-queues and renders again.
In-flight stock counts toward the fresh target, so a cold start doesn't
overshoot. Song briefs (requests and stock) run one at a time on the LLM,
turns granted in queue order (paid, then oldest free, then stock; not
first-come), while renders run in parallel, and each sees the genres of jobs still rendering
(§5.2 `genre_no_repeat`). A brief whose output was cut off (empty, or JSON
that never closes: an LLM limit or overload) re-queues its request without
spending an attempt, up to 4 times per request; after that it counts. A generator outage (transport error,
429/502/503/504) re-queues the request without spending an attempt and pauses
new jobs (15 s doubling to 2 min); jobs are never cancelled for a request.
`song_step()` runs one job inline (seed, tests, the simulation).

Stock songs stay spaced out: after a stock song finishes, the worker waits
`songs.stock_gap_s` (default 600 s) before starting the next one, even when
fresh stock is below target. Queued listener requests skip the gap and start
as soon as a slot is free; they do not reset it.

Song generation is the expensive path (~1.6 s of compute per 1 s of audio), so
stock production also has a library ceiling: once the library holds
`songs.stock_max_library` (default 100) usable songs, the stock worker stops
calling the song model entirely and only queued listener requests are
produced. The cap counts every non-retired song (aired ones recycle), so a
full library keeps the station on air without further generation. Setting it
to 0 disables the ceiling (RADIO §6.1, §12).

SFX are rendered by their own worker (`Producer.sfx_loop`), never at playout
and never in the voice worker's path: a talk clip is stored and airable as
soon as its voice is rendered, with its script cues kept as `sfx_pending`.
The SFX worker attaches overlays to pending clips oldest-unaired first, then
fills the evergreen stock pool one cue at a time (`seed.py` renders the pool
up front). A clip committed before its cues are ready airs dry. A failing SFX
backend only means hosts air dry.

Workers:
- **Song worker:** the decider above; up to C concurrent song jobs.
- **qwen38 worker:** priority order: contextual talk-ups (deadline-bound) >
  news refresh > song briefs.
- **ornith worker:** commercials and liners into inventory.
- **Kokoro worker:** renders approved copy in priority order (contextual >
  news > inventory).

### 6.2 Song pipeline

1. **Brief** (`qwen38`): returns JSON validated against a schema:
   `{title, artist, genre, style_prompt, lyrics}`.
   - Genre drawn from a weighted list in config (variety is the point), subject
     to the no-repeat rule.
   - **Style lock** (`genres.route_style`): a request that names a style routes
     to the nearest family and the caption's `Genre / Subgenre` must name that
     requested style. The validator also rejects a *positive* mention of a
     conflicting style's signature instruments (fiddle, banjo, pedal steel,
     steel guitar, dobro, twang, yodel, bluegrass, honky-tonk) in either the
     caption or the lyrics when the brief is not in the country/folk
     neighbourhood — negated mentions such as "no steel guitar" are allowed,
     because stating an exclusion is required. Rationale: the audio model sings
     the lyrics it is given and takes much of its feel from them, so a reggae
     brief carrying country-coded lyrics comes back sounding country. Rejected
     briefs are repaired once, then abandoned.
   - **Idiom lock:** under the same exemptions, stock Americana phrasing
     (`genres._AMERICANA_IDIOM`: county line, dirt road, tin roof, holler,
     y'all, …) is rejected in the caption and lyrics, and the caption must
     *negate* at least one of the excluded instruments (the explicit exclusion
     is enforced, not just requested). Rural subjects such as trucks, porches,
     hayrides, cornbread, cowboys and barn dances remain available in every
     genre; they do not specify the music's instrumentation or delivery.
   - **Sound sheets** (`genres.sheet_text`): the pinned family's (or the
     requested style's, e.g. reggae, bossa nova) groove, core instruments,
     native scene, exclusion and lyric idiom are sent with the brief prompt.
   - **Inferred style:** when a request names no style the router knows
     (misspelling such as "jass", or an indirect description), the brief
     JSON adds `requested_style` (1–4 plain words, or `""`). A non-empty
     value is validated like a routed style: it must be named in
     `Genre / Subgenre`, must match its routed family when it has one, and
     turns on the style and idiom locks.
   - **Creative direction:** `song_brief.md` supplies the shared musical
     contract. Exactly one of `station_song.md` (stock/free) or
     `paid_request.md` (paid, including operator comps) is appended to the
     **system** prompt, selected from the request's server-side priority.
     Missing direction templates fail the brief before any generation.
   - **Stock songs and free requests get the Pilgrim Dot Farm treatment:**
     tongue-in-cheek rural character belongs in the title, artist and sung
     story, in the chosen style's own idiom. Preserve a free request's subject
     and musical style while bringing it into the station's farm world.
     Full farm stories are welcome, with no one-image limit; PILGRIM DOT FARM
     may slip naturally into lyrics and hooks. No exact station-name or farm
     keyword quota is enforced. Instrumentals carry the character in title
     and artist. A station-name title tag ("(PILGRIM DOT FARM)") is rejected
     for stock/free songs; a funny title alone is not the requested lyric
     treatment. The musical caption stays focused on the requested sound.
   - **Free/stock songs lead with the chorus:** listeners scroll past, so
     the hook has to land in the first seconds. `station_song.md` asks the
     brief LLM to open the lyrics on `[chorus]` with no `[intro]` before it,
     and code (`pipelines/songs.py` `lead_with_chorus`) moves the first
     `[chorus]` block to the top and drops a leading `[intro]`, so the shape
     is guaranteed without rejecting or re-briefing. Only the leading position
     is prescribed; the rest of the song's structure is the LLM's. Paid songs
     and verbatim lyric sheets are never reordered.
   - **Paid songs follow the customer's brief:** no unsolicited farm humor
     or station branding in lyrics, caption, title or artist. Preserve named
     titles and artists, including a requested parenthetical title. A requested
     farm subject is welcome without adding an unsolicited station name.
     These creative directions are prompt requirements, not keyword filters.
   - **Payer's own MiniMax input** (PAYMENT.md Step 12c): when a paid request
     contains a structured caption and/or tagged lyrics, the brief LLM reads
     the request in any English and returns `caption_verbatim` /
     `lyrics_verbatim`; code (`pipelines/verbatim.py`) then copies those
     blocks from the request exactly (only section tags are normalised). The
     LLM writes only the missing parts. Verbatim parts skip the style, idiom
     and caption length/content checks; structure checks still apply.
     A supplied caption routes on its own Basic Attributes line. Free requests
     always receive the station treatment, even if they contain tagged lyrics
     or a structured caption; verbatim flags are ignored for free requests.
   - Stock/free artists may be drawn from the station bible's recurring
     fictional artists (§7), or invented; paid artists follow the brief.
   - Lyrics of arbitrary length. The request sends `duration_seconds` =
     `songs.max_duration_s` (360 s) as the ceiling; the model may end sooner.
     (Supersedes OVERHAUL 3.1, which sent no duration: without it mlx-serve defaults to 60 s and
     cuts every song there. `duration_s` is silently ignored.)
2. **Generate** on the backend pool (`songs.gen_backends`): one synchronous
   POST `{url}/v1/audio/music-generations` returns the WAV inline. A
   `auth: litellm` backend gets `model: models.music` and the Bearer
   `LITELLM_TOKEN`; the proxy's least-busy router spreads renders over the
   three deployments when they arrive at least `songs.submit_stagger_s` apart.
   The pool never runs more than a backend's `slots` renders (nothing upstream
   refuses extras: a box would take a 2nd render and halve both). Requests
   lease the fastest idle backend (EWMA real-time factor), stock the slowest.
   A backend that fails at transport level sits out `songs.backend_cooldown_s`
   (doubling to 600 s). The song's `meta` records `backend` and `generator`
   (the `x-generated-by` header; a seed replays only on the same generator).
   Record wall-clock generation time for the rate metric.
3. **QC** (§8.1).
4. **Normalize and encode** (§8.2); store the brief as metadata. QC and
   normalize run in a worker thread: the scheduler and HTTP server share the
   event loop.

### 6.3 Voice pipeline

1. **Copy** (LLM by role): returns JSON
   `{text, role, est_duration_s, evergreen, expires_at?, gags_used[], gravity?}`.
2. **TTS cleanup:** strip markdown, emoji, bracketed stage directions, and
   asterisks; expand times ("10:30" → "ten thirty"), numbers, and
   abbreviations; reject copy containing URLs. "Pilgrim Dot Farm" is already
   TTS-safe.
   **Token contract (ANNOUNCER §A2/A6):** copy for `dj_talk`, `time_check` and
   `promo` carries `[[clock]]`, `[[day_part]]`, `[[day]]`, `[[event_name]]`,
   `[[days_until]]` or `[[cta]]` tokens; the code fills them, never the LLM.
   In those roles a bare clock time or a relative day word ("tonight",
   "tomorrow", "this Thursday") is **rejected**, not rewritten. News and
   commercials are exempt: a spot saying "open till six" is correct and
   `tts_cleanup` keeps rewriting it. `time_check` text is code-written and
   never reaches the LLM.
3. **Render** via Kokoro (`GET /tts?text=...&voice=...&speed=...&format=wav`),
   voice chosen by role (§10).
4. **QC** (§8.1), then **normalize and encode** (§8.2).

Duration targeting: calibrate seconds-per-word for each voice/speed at setup
and store it. Prompts request a word count that yields the target duration;
QC rejects clips more than ±25 % off target.
- **Operator phrases (literal text, TUI.md §6):** the operator's typed words are
  the copy (no LLM rewrite or invention). The mandatory TTS cleanup runs on
  submission; the operator sees and confirms the exact cleaned text; the
  confirmed text is hashed with the character/config version and that confirmed
  version is what renders (a validation race can never change the spoken
  words). Render via the existing Kokoro client in a per-job staging directory
  **outside** `pilgrim/library/` with unique filenames, then run the same QC,
  two-pass normalization (−16 LUFS / −1 dBTP) and FLAC delivery (§8). Only a
  QC-passed clip is published as a new immutable FLAC and exposed as ready;
  existing library files are never overwritten or removed.

## 7. Running gags — station bible + airplay ledger

Two separate stores:

**Station bible** (`bible/*.md`, creative canon, prose). Seed content for
Phase 1:
- DJ persona and on-air voice.
- 3 recurring fake sponsors and 1 recurring medication (with a side-effect list
  that can grow over time).
- 2–3 recurring fictional artists with signature genres.
- A fictional town and a few recurring locals.
- Style guide: tone, banned topics, length norms.

Writers **read** the bible (relevant excerpts injected into prompts). In
Phase 1 the bible is edited by hand only. Phase 2 adds a continuity step that
*proposes* additions for review.

**Airplay ledger** (`station.db`, structured, owned by the scheduler): what
actually aired and when, play counts, last-aired times, gags used. Airplay is
recorded from client heartbeats, not from what was produced. Prompts receive
ledger facts ("the Glue-Free Glue sponsor last aired 2 h ago; the medication's
side-effect list was last extended yesterday") so gags can escalate and
callbacks make sense.

**DJ operator ledger and rotation accounting (TUI.md §6–7):** a distinct record
per operator command (command ID, payload hash, accepted epoch/revision,
operation, outcome, applied revision, affected occurrences) and per phrase job
(original/cleaned text, character/voice snapshot, status, media link, QC
result, expiry, failure reason), with unique publication per command/job.
Rotation accounting separates scheduled **reservations** from actual
started/partial-play history, so an edit can release/recompute reservations
without erasing prior real airplay, and a cancelled request occurrence never
becomes `aired` merely because the playhead moved past its old sequence.

**Persisted rotation (PRIORITIES §4):** `items` carries `last_aired_at` (wall
epoch, set at commit) and `play_count` so song spacing and Tier-2 weighting
survive a restart. A `NULL` `last_aired_at` means never aired (or aired before
the ledger) and counts as unheard-forever (`wait = 1.0`). These are backfilled
once from `airplay` (`MAX(recorded_at)`, `COUNT(*)`) for songs that predate
the columns.

## 8. Audio quality

### 8.1 QC (the "grader")

Every item passes before entering inventory:
- **Duration** within bounds for its type/target.
- **Silence detection:** reject items that are mostly silent or contain
  internal dropouts > 2 s (songs) / 1 s (voice).
- **Clipping** check.
- **Abrupt ending** check for songs: the last ~0.5 s is compared to the
  track's *median* 1-s level (body-relative, OVERHAUL 3.2). This is
  **recorded** (`verdict.abrupt_end`, `meta.abrupt_end`) but **never fails**
  the song — the producer applies a fade-out instead.
- **Copy checks** for voice: length, banned content, TTS-hostile characters
  (post-cleanup).

Failures are logged with reason and discarded; the producer refills.

### 8.2 Normalization and encoding

- Loudness-normalize everything to **−16 LUFS integrated, −1 dBTP** (ffmpeg
  `loudnorm`, two-pass).
- Trim leading/trailing silence below −50 dBFS, leaving a consistent pad
  (~150 ms), so joins sound like a station rather than dead air or collisions.
- `normalize(src, dst, cfg, fade_out_s)`: when > 0, the tail chain runs
  `areverse,trim,fade-in,areverse` (a fade-in on reversed audio is a fade-out
  on the original). The producer uses this (`songs.abrupt_fade_s`, default
  2.5 s) for songs with hard endings.
- Resample everything to **48 kHz** (`audio.sample_rate`) and deliver
  **stereo** (mono speech is duplicated); the browser's AudioContext
  resamples on decode as before.
- Deliver as **CBR MP3** (`libmp3lame`; `audio.mp3_kbps` 192 for stereo
  sources, `audio.mp3_mono_source_kbps` 96 for mono sources) with the
  LAME/Info **gapless header** (encoder delay + padding). Browsers trim that
  padding in `decodeAudioData`, so joins stay sample-contiguous — but WebKit
  (Safari, every iOS browser) only honours it for **stereo MPEG-1** files;
  mono or 24 kHz MP3s keep ~576 samples of lead-in there (docs/backends.md
  §9). That is why the rate and channel count are fixed. `encode_mp3`
  verifies `delay + frames + padding == MPEG frames × 1152` and rejects a
  file without the header. *(Operator decision 2026-11-01; supersedes FLAC
  delivery. Pre-switch FLAC files stay on disk as masters, hard rule 5.)*

### 8.3 Emergency pack

A small set of songs, liners, and station IDs flagged `emergency`: never
deleted, never subject to repeat rules, stored locally on the M5. Used only
when everything else is unavailable. The producer keeps
`inventory.station_ids_min` emergency station IDs (timeless copy, type
`station_id`), so there are words between songs even right after a library
wipe; `clear_library --keep-songs` keeps the pack.

### 8.4 Media delivery — S3 + CloudFront

S3 is the source of truth for listener audio; the M5 no longer streams it
(operator decision 2026-11-01).

- A **media publisher** task in the station process (`pilgrim/media_publish.py`,
  started with the scheduler/producers; never inside them, hard rules 1 and 3)
  scans for items whose `media_path` is an MP3 and `s3_key` is NULL, and
  uploads each to `media.bucket` under
  `media.key_prefix + <type>/<file stem>-<sha256[:16]>.mp3` with
  `Content-Type: audio/mpeg` and `Cache-Control: public, max-age=31536000,
  immutable`. The key is content-addressed, so a key never changes bytes.
  Only after a successful PUT does it set `items.s3_key` / `uploaded_at`.
  A failed upload is logged and retried after 5 min; it never blocks or
  crashes anything.
- CloudFront (`media.public_base_url`) is the only reader of the bucket. The
  program and state APIs (§11) give each item
  `url = public_base_url + "/" + s3_key`.
- **Fallback:** an item not yet uploaded gets `url = /api/media/<id>` (the
  origin route, served through the edges as before). Publishing normally
  completes seconds after an item is rendered, well inside the ≥5 min
  committed window, so this path is transitional.
- Emergency items (§8.3) are never published: they are local by definition
  and keep the fallback URL.
- **Cover art (ALBUM_ART.md).** The same publisher loop uploads each song's
  rendered JPEG (`art_path` set, `art_s3_key` NULL) to
  `art.key_prefix + <song media stem>-<sha256[:16]>.jpg` with
  `Content-Type: image/jpeg` and the same immutable `Cache-Control`, and sets
  `art_s3_key` / `art_uploaded_at` only after a successful PUT. Failures share
  the 5-minute retry. CloudFront already fronts the whole bucket, so art needs
  no new infrastructure. Unlike audio there is **no origin fallback**: the API
  sends `art_url: ""` until the upload lands, and art is cosmetic, so a song
  simply airs without a cover meanwhile.
- Nothing is deleted from S3 yet (no lifecycle; operator decision 2026-11-01).
- Cover-art backfill: `make art-backfill ART_ARGS="--apply --limit N"` (dry
  run by default; `--item ID --force --seed N` re-renders one song). It reuses
  the worker's per-song path and memory gate, is resumable, and refuses
  `--apply` while the live worker holds a fresh lease (two renderers must never
  contend for the single-flight FLUX server).
- Backfill: `make mp3-migrate MIGRATE_ARGS="--apply --upload"`
  (`pilgrim/tools/mp3_migrate.py`) encodes an MP3 next to every non-emergency
  FLAC, repoints the row (after a SQLite `.backup`), and uploads. Resumable.
- `make media-smoke` round-trips one 2 s tone through S3 and CloudFront and
  checks status, type, cache and CORS headers. Real backend: only when asked.
- `make art-smoke` (ALBUM_ART.md Step 10; only when asked) renders one
  1024×1024 cover of a fixed test title, checks the PNG dimensions, encodes the
  JPEG, PUTs it to `art/smoke/`, GETs it through CloudFront (200 +
  `image/jpeg`), and saves the PNG to `pilgrim/logs/art-smoke.png` for a human
  to eyeball.
- `make reel REEL_ARGS="--item ID [--start S] [--duration D]"` (ALBUM_ART.md
  Step 11) builds an Instagram Reel from the **published** copies — the song's
  MP3 and cover JPEG fetched through CloudFront — as 1080×1920 H.264 High /
  AAC 48 kHz stereo 192 kb/s at 30 fps with `+faststart`, verified by
  `ffprobe`. Output: `pilgrim/logs/reels/<stem>.mp4`. Uploading to Instagram
  is out of scope.
- CORS: browsers `fetch()` the CloudFront URL cross-origin from the site, so
  every response must carry `access-control-allow-origin`. A CloudFront
  Function (viewer-response) sets `*`; the managed CORS policy drops the
  header whenever the request carries a `priority` header (docs/backends.md §9).

  now: 69.N+10**, where N is the integer live listener count (`listeners` on
  `GET /api/station/state`, §14) plus a constant offset of 10 (operator
  decision, 2026-10-03), polled every 15 s; `69.10` until the first poll, and
  a failed poll keeps the last value (operator decision, 2026-10-02).
- **OFF AIR**: when an edge cannot reach the origin it answers `/api/health`
  with `{"on_air": false, "off_air": true}`; the page shows the OFF AIR
  banner and disables PLAY. While playing, health alone never stops audio;
  the program/media fetches decide. A 503 with `off_air: true` is definitive:
  already-buffered audio plays to its end, then the client stops and shows
  OFF AIR. Any other failure (network blip, other status, decode error) is
  retried every 1 s and ends the session only after 10 s of consecutive
  failures with the buffer dry (`OFFAIR_GRACE_MS`); any success resets it. The request
  line shows `The station is off the air. Requests are closed.` on a 503 with
  `off_air: true`, and a failed GET keeps the last rendered board.

### 9.2 Playback engine

- The `AudioContext` is created inside the PLAY click handler (satisfies
  autoplay policy).
- **Mobile continuity (2026-11-04).** All decoding and scheduling stays in
  Web Audio, but the graph's output goes through **one persistent `<audio>`
  element** (`#sink`, fed by a `MediaStreamAudioDestinationNode`, played once
  inside the PLAY gesture). Phones treat a page playing a media element as
  media playback: it keeps playing in the background and when the device is
  locked, uses the media volume rather than the ringer, and gets lock-screen /
  notification controls. This is a single output sink for the whole session,
  never a per-item element or a handoff between elements (hard rule 9 still
  holds: joins are sample-accurate `AudioBufferSourceNode.start(when)` on one
  context). If the element cannot play (old browser, policy), the graph
  connects straight to `ctx.destination` (`sink: direct`). Before the context
  is created, PLAY sets `navigator.audioSession.type = "playback"` (Audio
  Session API, Safari 17+; a no-op elsewhere) so iOS does not mute Web Audio
  with the ringer switch. The **Media Session API** carries the audible song's
  title/artist/cover (from the same `pd:nowplaying` decision as the label,
  never the next song early); lock-screen *pause*/*stop* is STOP and *play*
  restarts. A context that stops running (`interrupted` on iOS, `suspended`
  elsewhere: a call, Siri, another app, the OS pausing the page) is resumed
  on its `statechange`, on `visibilitychange`/`pageshow`/`focus` and every
  2 s while interrupted; the audio clock pauses with it, so buffered sources
  continue where they stopped, and an interruption of 5 s or more rejoins the
  live programme through the revision-reset path. Heartbeats carry playback
  telemetry (`platform`, `ctx_state`, `hidden`, `sink`, `resumed`; §11) so
  background/lock behaviour on phones is measurable from the admin health
  and the `listener.telemetry` log lines. Verified with Playwright only for
  the sink element and Media Session metadata; the background/lock/ringer
  behaviour needs a real iPhone and Android device (or emulator).
- **`pd:nowplaying` (VOTING.md).** `player.js` dispatches a `CustomEvent` on
  `document` from the same audio-clock decision as the song label: detail =
  `{epoch, seq, media_id, title, artist}` for the audible named song, else
  `null` (also on STOP). `rating.js` listens to it and never touches audio; it
  polls `/api/station/state` every 5 s only while its row is enabled.
- Fetch the committed program; keep the **next 2 items fetched and decoded**
  ahead of the current one, and keep decoding further (up to 5 ahead) while
  that holds less than 60 s of scheduled audio, so a run of short talk and
  liners can't leave a slow fetch exposed. Audio (items and SFX overlays) is
  fetched from each entry's `url` (CloudFront, §8.4), falling back to
  `/api/media/<id>` when absent. A media fetch that gets no headers or bytes
  for 8 s is aborted and retried once from `/api/media/<id>` (a different
  host, so a different connection): browsers can hang on a dead pooled CDN
  connection for a minute or more.
- Schedule each `AudioBufferSourceNode` with `start(when)` at exactly the
  previous item's end time on the AudioContext clock (sample-accurate joins).
- Send a heartbeat `{seq, position, player_id}` every 5 s and on each item
  start (`player_id` is the page's per-tab ID; it feeds the live listener
  count, §14).
- **Client-side last resort:** the page ships 2–3 tiny embedded liners
  (base64). If the next item isn't decoded when needed (network hiccup), play
  one and log an `underrun` event to the server.
- Release decoded buffers after playback (a 3-min 48 kHz stereo song decodes
  to ~70 MB of float32).
- **SFX overlays** (`sfx` on a program item): decoded in the background,
  never awaited, and started as a second `AudioBufferSourceNode` at
  `host start + offset_s` with their own `GainNode` (`gain`), stopped at the
  host's end. The host's gain dips to `duck` under a stinger so two full-level
  sources don't clip. An overlay that isn't decoded in time, or whose beat
  already passed when joining mid-clip, is skipped (a bed resumes at the right
  point). Overlays never move a join.
- **DJ coordination (TUI.md §5, §9.2).** The client polls the cheap
  `GET /api/station/state` (epoch/revision/current+offset/prepared cutover)
  independently of its buffered programme length. On a revision change it
  cancels obsolete scheduled sources, stops their SFX, releases their buffers
  and ignores stale fetch/decode completions — explicit source references are
  held by occurrence (`_src`/`_gain`), so a reset can stop the future without
  touching the audible item; the new snapshot is then rescheduled from that
  item's audio-clock end (or cut over to the snapshot's on-air item when the
  current occurrence vanished). This is what makes a spliced listener request
  air at the next boundary. On an
  activated cutover it maps server time to the AudioContext clock, starts the
  successor at that boundary, applies a brief configured anti-click fade and
  stops the skipped source at the same boundary; for queue-next it keeps the
  natural current-item end. Heartbeats carry player ID, protocol version,
  observed epoch/revision and a readiness summary; readiness never controls
  production. Target: an acknowledged skip within a configurable 2 s budget for
  healthy clients; a lagging/disconnected listener may stay on old buffered
  audio and rejoin at the latest offset — never silence everyone waiting for
  one slow client. With no active listeners the server applies a validated edit
  without waiting for a browser.
- Background/locked playback on phones is handled by the persistent output
  sink + interruption recovery above. Known limitation: a page the OS has
  killed outright (battery optimisation, memory) cannot resume itself.

**Listeners (SPLIT_PLAN §1).** One station process serves two HTTP listeners.
The **public** listener (`station.host:station.port`; loopback `:5080` on the origin)
serves only the edge-facing routes: `GET /api/station/program`,
`GET /api/station/state`, `POST /api/station/heartbeat`,
`GET /api/media/{id}`, `GET|POST /api/requests`,
`POST /api/requests/{id}/vote`, `POST /api/station/rating`,
`POST /api/visitors`, the
paid routes (`POST /api/paid-requests`, `GET /api/paid-requests/{token}`,
`POST /api/paid-requests/{token}/checkout`, `POST /api/stripe/webhook`), and
`GET /api/health`. Its `/api/health` returns only
`{"on_air", "art": {"backend"}, "time"}` and performs no backend, inventory or
database probe — `art.backend` is the art worker's cached `ok|down|busy`
(`disabled` when off), never a live FLUX call, because a render blocks the
image server for ~40 s (ALBUM_ART.md Step 5). It is the only health shape a
browser or edge sees. Any other `/api/*` path on the public listener is `404`. The
**admin** listener (`station.admin_host:station.admin_port`; loopback `:5081`)
is a superset: every route above plus `/api/station/start`,
`/api/station/stop`, `/api/admin/voices`, and every `/api/admin/dj/*` route,
with the full health payload. `/api/admin/*` is admin-only and must never be
reachable through an edge; production binds the admin listener to loopback.
The static client is mounted on the public listener only when
`station.serve_web` is true (single-host runs); edges serve `pilgrim/web/`
themselves.

**Idle (IDLE.md).** With `idle.enabled`, the station freezes the playhead
and pauses production when no player has heartbeated for `idle.after_s`
(§3). Only `GET /api/station/program`, `POST /api/station/heartbeat` and the
admin DJ mutation (`POST /api/admin/dj/play`) wake it; `GET /api/health`,
`GET /api/station/state`, `GET /api/requests`, `POST /api/visitors` and
`GET /api/media/{id}` never do (idle pages, bots and smoke checks poll
those). Both nginx hops allowlist the two voting paths; the origin's own
limiter (`voting/ratings.per_client_per_10min`) is the per-listener ceiling.

**Caching (SPLIT_PLAN §2).** The origin states cache intent once, so edges and
Cloudflare only have to honor it:

| Route | `Cache-Control` |
|-------|-----------------|
| `GET /api/media/{id}` (200) | `public, max-age=31536000, immutable` |
| `GET /api/media/{id}` (404) | `public, max-age=30` |
| `GET /api/station/program` | `public, max-age=1` |
| `GET /api/station/state` | `public, max-age=1` |
| `GET /api/requests` | `public, max-age=2` |
| `GET /api/health` (public) | `public, max-age=2` |
| every POST | `no-store` |
| static web files | `no-cache` from the origin mount; an edge sets its own `public, max-age=60` |

A media id always maps to the same bytes: every pipeline writes a new file
before `add_item()`, retiring keeps the file, and purging deletes it (no
in-place rewrite exists). The one exception is the one-time MP3 backfill
(§8.4), which repoints an id from its FLAC to an MP3 of the same audio; an
edge or browser still holding the cached FLAC decodes it just the same.
CloudFront objects carry their own `immutable` header from S3 (§8.4). The `max-age=1` on `/api/station/state` means
`server_time` can be up to about 1 s old at the client; DJ cutovers use
`cutover_lead_s: 1.0` (§5.5), which this plan does not change.

`no-cache` on the static web files is a **revalidate**, not a no-store: the
browser keeps the file but asks the origin whether its ETag still matches, so
a web edit reaches listeners on the next page load without a server restart
and without a build step or a cache-busting filename.

**Edge-generated off-air responses (not origin).** When an edge (or the
gateway) cannot reach the origin, it answers by itself. The edge also
intercepts an upstream-sent bare `502`/`504` (Tailscale serve sends one when
the gateway nginx is down while tailscaled is up) and substitutes the same
bodies; the origin's own 4xx and the gateway's 503 pass through untouched.
`GET /api/health` →
`200 {"on_air": false, "off_air": true}`; any other `/api/*` →
`503 {"off_air": true, "detail": "station is off the air"}`. These bodies are
generated by nginx at the edge/gateway, never by `server.py`; the origin's own
4xx/5xx responses pass through untouched. A `504` on `POST /api/requests` is a
slow moderation call, not an outage: the edge returns
`504 {"detail": "request timed out"}`. `/edge-health` never contacts the
origin, so a load balancer does not kill healthy edges during an origin
outage.

**Operator authentication.** Every `/api/admin/dj/*` route requires a dedicated
bearer token from **`PILGRIM_DJ_TOKEN`** (env; documented in README.md; never
reuse `LITELLM_TOKEN`). Missing credentials (401/403) disable DJ mutations
without affecting the public request line. Remote operation uses the
deployment's encrypted connection or an SSH tunnel.

## 14. Storage

Songs are kept (recycled), delivered as MP3 (§8.2): roughly 4.3 MB per
3-min song at 192 kbps (speech at 96 kbps, ~0.7 MB/min). Every delivered
file also lives in S3 (§8.4); pre-switch FLAC masters stay on the M5. At continuous generation that's several GB per day. Phase 1 uses
`library.soft_cap_gb` to throttle generation once the pool is large; pruning
policy is Phase 3.

The `items` table carries `s3_key TEXT` (object key in `media.bucket`; NULL =
not uploaded) and `uploaded_at TEXT` (§8.4), both added by an idempotent
migration. `set_media_file` (MP3 backfill) clears them so the new file is
re-published.

**Cover art (ALBUM_ART.md, §8.4).** The `items` table carries four additive,
idempotently-migrated art columns: `art_path TEXT` (absolute path of the local
JPEG master; NULL = no art yet), `art_s3_key TEXT` (published object key; NULL
= not uploaded), `art_uploaded_at TEXT` (ISO time of the successful PUT) and
`art_attempted_at REAL` (epoch of the last failed attempt, for the
`art.retry_after_s` back-off). Songs only (`type='song'`, not retired, not
emergency, both title and artist non-empty). The master PNG and the delivered
JPEG live in `pilgrim/library/art/` as **new** files named after the song's
media stem (`<stem>.png` / `<stem>.jpg`, then `-2`, `-3` on collision) — never
an overwrite (hard rule 5). `meta_json.art` stores the scene, the final FLUX
prompt and the seed so a render is reproducible. `art_path` is set only after
the PNG validates and the JPEG encodes; `art_s3_key` only after the PUT.

The `items` table carries a `retired` flag (default 0) — a soft-delete used to
pull truncated/unusable inventory out of playout and production while keeping
the row for history and the file on disk. `get_item` still returns retired
rows (media endpoint + history); `list_items` and the count helpers exclude
them. The flag is set by `python -m pilgrim.tools.audit_library` (OVERHAUL 2.2)
or `store.retire_item(id, reason)` (reason merged into `meta_json`).

The `requests` table carries lifecycle columns (`attempts`, `song_item_id`,
`intro_item_id`, `updated_at`, `prep_started_at`, `due_at`, `claimed_at`) and statuses `queued -> producing -> ready ->
aired`, plus `rejected`, `evicted`, `failed` (legacy `serviced` reads as
`aired`; OVERHAUL 4.4). `prep_started_at` is stamped by `mark_request_writing`
when the request gets its turn at the brief LLM and the lyrics/brief are
written (the producer's `writing` stage), and again on every retry, so the
board's Prep Time (`aired_at - prep_started_at`) measures prep work, not
queue idle: a request that sat in line overnight no longer reads as a
multi-hour prep. A row that never recorded a writing start (aired before the
column existed) sends `wait_s: null` and the page shows an em dash (`—`): the
measurement is missing, not zero, and not the queue wait.
`due_at` (ISO wall time, additive migration) is stamped by `mark_request_due`
when the song is committed or spliced: the slot's wall time (`_slot_wall`),
which while frozen is "now + distance from the frozen playhead" — when it
would air if woken now. The board's Prep Time stops at the earlier of
`aired_at` and `due_at` (§11). A request becomes `aired` when the playhead reaches
its song, not when the song is committed; until then it stays `ready` ("up
next"). The request's song and intro enter the library together with the
`ready` flag, so the song can never air bare as stock first. Only `queued` rows are ever FIFO-evicted; a crash
mid-generation is reset `producing -> queued` on station start. A backend **transport** error (generator unreachable / connection dropped)
returns the request to `queued` without spending an attempt, and the song
worker backs off 15 s doubling to 2 min; only real failures (bad brief, QC)
count toward the 3-attempt `failed` limit. A request's named genre/style
overrides `songs.genres`; the list is only a fallback for requests that name
no style. The public request line does **not** FIFO-evict (`add_request(cap=None)`):
every accepted request is made; `queue_cap` (50) only bounds the board display.
At `requests.free_queue_max` (100) free requests waiting (queued, producing or
ready), a new free request is refused unstored (`line_full: true`); no waiting
request is ever dropped, and paid requests are never capped. Paid rows show a
one-sentence LLM summary (`paid_summary.md`) on the board; labels that fell
back to raw text are regenerated at startup.
With >= 3 queued, request briefs ask for a short (60-90 s) song to drain the
backlog. Every request song gets an intro that opens with a listener-request
shout-out: two LLM-written tries, then a scripted "Request line! You asked, we
made it! Here's <title>, by <artist>!" rendered directly.

**Community votes (VOTING.md).** Two additive tables, created idempotently on
open (an old `station.db` gains them and `requests.claimed_at` without a
rewrite):

- `request_votes(request_id, voter_id, ip, value, created_at, updated_at)` —
  PRIMARY KEY `(request_id, voter_id)`, `value` ∈ {−1, +1}; a retraction (0)
  deletes the row. `ip` is the canonical client IP, stored for the per-target
  abuse cap only.
- `song_ratings(id, item_id, epoch, seq, voter_id, ip, stars, created_at,
  updated_at)` — `UNIQUE (epoch, seq, voter_id)`: one rating per **airing**,
  `stars` 1–5 (`CHECK`), `item_id` feeds the lifetime aggregate.

Aggregates are computed from these tables on every read (SUM/COUNT/AVG),
never cached on `requests`/`items` (VOTING.md V9), so retractions and
re-votes need no bookkeeping. **Queue order** (one `store.queue_order()`
helper, used everywhere): `priority DESC`, then in-flight
(`producing`/`ready`) before free `queued`, then free `queued` by vote score
DESC, then `COALESCE(paid_at, claimed_at, created_at)` ASC, `id` ASC. This
supersedes PAYMENT.md §3.2's pure FIFO; with no votes it is identical.
`claimed_at` is stamped once by `mark_request_producing` (kept across
retries), so in-flight order is claim order and a finished request's
`_wait_turn` order agrees with the splice. `pending_requests` excludes buried
free rows so the scheduler does not hold the committed window for a request
nothing will produce.

**Paid requests (PAYMENT.md).** Paid rows have `priority=1` and the payment
columns (`public_token`, `paid_at`, `amount_cents`, `currency`,
`checkout_session_id`, `payment_intent_id`, `livemode`, `reconciled_at`,
`summary`). Step 12b adds `stage TEXT` and `comped INTEGER DEFAULT 0` and the
pre-payment status `checking` (stages `moderation -> copyright -> ready`):`checking -> rejected` (moderation / copied lyrics / crashed check),
`checking/ready -> awaiting_payment` (checkout claimed once), or, for an
operator comp, `checking -> queued` with `comped=1`, `amount_cents=0` and no
Stripe session. `checking` rows are never on the board and are `abandoned` on
station start (their background task died with the process).

**Visitors.** A separate `visitor_ips(ip TEXT PRIMARY KEY, first_seen REAL)`
table stores the **raw canonical client IP** (operator decision, 2026-10-01;
supersedes the earlier HMAC-only `visitor_signatures` table, which is
dropped). One distinct canonical public client IP counts once for the
lifetime of the counter; the count starts at 0. The IP is resolved through
the deployment's trusted-proxy chain. Each hop passes the browser IP on and
the edge always overwrites whatever the client sent:

| Hop | Trusts | Sets `X-Real-IP` to |
|-----|--------|---------------------|
| Edge nginx | Cloudflare's IP ranges (prod) / nobody (local) | `$remote_addr` after `real_ip` processing (the browser) |
| Gateway nginx | the edge peers that reach it (tailnet in prod, loopback locally) | the edge's `X-Real-IP`, unchanged |
| Origin | `visitors.trusted_proxies` (single IPs **and** CIDRs) | reads `X-Real-IP`; falls back to the first `X-Forwarded-For` entry |

A peer is trusted only when its canonical address is inside a configured
network. From an untrusted peer both headers are ignored and the socket peer
address is used, so a spoofable header cannot reach the counter. This is
the **only** trust decision: both uvicorn listeners run with
`proxy_headers=False`, so uvicorn never rewrites the peer from
`X-Forwarded-For` first. The request-line rate limit (4.3) keys on the same
resolved client IP, not the socket peer (behind the gateway every request
shares one peer). When no
canonical identity can be resolved, registration is skipped and the current
count is returned; the counter never breaks radio/requests. Raw IPs are
personal data: no retention/pruning policy is implemented yet.

**Live listeners.** Not stored: the server keeps an in-memory map of
heartbeat `player_id` → last heartbeat time (injected clock). A player counts
while its heartbeats arrive within `visitors.listener_timeout_s` (default
15 s, three missed 5 s heartbeats), so STOP or a closed tab drops out within
that window. It counts players, not people (one per playing browser, since
tabs hand off playback), and resets on restart. New IDs beyond
`visitors.max_listeners` are ignored; `player_id` is client-supplied, so the
count is indicative, not authenticated.

**DJ persistence (TUI.md §6–7; design only — additive migrations are prepared,
tested against temporary databases and reviewed with the operator before any
live change; the TUI never runs them):**

- `dj_commands(command_id PK, payload_hash, accepted_epoch, accepted_revision,
  operation, outcome, applied_revision, affected_seqs, created_at, updated_at)`
  — unique publication per command; identical retry returns the existing row.
- `phrase_jobs(job_id PK, character_id, voice, speed, original_text,
  cleaned_text, text_hash, status, media_item_id, qc_result, attempts,
  expires_at, created_at, updated_at)` — one publication per job; cancelled
  scheduled phrases are terminal (never auto-replayed).
- Programme **occurrence history**: superseded/skipped occurrences keep their
  identity (a sequence number is never reused for a different item, §5.3) with
  revision/cutover metadata, so rotation accounting can separate reservations
  from real airplay (§7). `items` accepts the `operator_phrase` type with meta
  linking to its character/job; media identity stays `items.id`.

## 15. Testing

Random selection is chosen for Phase 1 partly because it is easy to test.

**Fakes** (`tests/fakes/`):
- `fake_minimax`: returns a tone WAV of the requested length after an
  RTF-scaled delay (scalable for accelerated tests; can inject failures and
  bad output).
- `fake_kokoro`: returns a tone/noise WAV sized from word count.
- `fake_llm`: returns canned valid and invalid JSON.
- `fake_sfx`: returns a 48 kHz mono tone of exactly the requested
  duration (like MOSS-SoundEffect); can inject outages.

**Simulated clock:** scheduler and producers take a `Clock` interface. Run
**24 simulated hours in seconds** and assert:
- Committed window never drops below target (after seed).
- No two items overlap or leave a gap in the program timeline.
- All §5.2 constraints hold (spacing, expiry, adjacency, genre repeats).
- Observed segment mix is within tolerance of configured weights.
- Fallback chain engages correctly when backends are killed mid-run.

- Words between songs: every pair of songs has a liner / station ID /
  DJ talk / field report / intro between them (zero bare gaps). Unit tests
  cover the cold start (songs + spots + emergency IDs only) and that the
  emergency IDs stay off air while liners exist.
- SFX policy: no overlay on news or any non-host type, every overlay inside
  its host, ≤3 stingers in any 10 s, joke rimshot rate ≈ 50%; field reports
  never adjacent to news.
- **PRIORITIES §6 (sim):** with songs produced at a steady rate over 24 h,
  songs < 12 h old get *more* airtime than their time-averaged pool share; no
  eligible song goes unheard longer than `max(6 h, pool_size × mean gap)`
  (starvation guard).
- **ANNOUNCER §A1 (sim):** no committed `dj_talk`/`news`/`time_check` airs
  after its `expires_at`, measured on the committed timeline (SimClock).
- **ANNOUNCER §A3/A4 (sim):** every `time_check` speaks the 5-minute bucket it
  actually airs in; ~4 clock reads per hour, one per mark; no `time_check`
  adjacent to `dj_talk`, `news` or another `time_check`.
- **ANNOUNCER §C1/C2 (sim):** promo airings follow the campaign ramp; every
  campaign promo contains the station name and the label; a `promo` is never
  adjacent to `dj_talk` or another `promo`.
- **Steady self-promotion (sim):** each promo kind keeps its own gap
  (`request_line_gap_s`, `paid_tier_gap_s`, `tree_fiddy_gap_s`); paid-tier and
  Tree Fiddy promos both air in a 24 h run; the Tree Fiddy Report carries the
  real 7-day paid count.
- **ANNOUNCER §A5 (sim/DB):** a greeting never contradicts the air time when
  the same voice spoke immediately before; a new voice may greet.
- **ANNOUNCER §B4/B5 (sim):** no liner repeats inside
  `liners.repeat_gap_items`/`repeat_gap_s`; recycled songs air with their named
  intro when one exists.

**Scheduler unit tests (PRIORITIES §6):**- Restart regression: a recycled pool with no persisted history does not open
  with the lowest id; across seeds the first pick favors the newest third.

**Idle (IDLE.md, `test_scheduler.py` / `test_producer.py` / `test_server.py`):**
- `freeze()` holds `position()`/`coverage()`/`on_air()` for an hour; `thaw()`
  resumes at the same offset into the same item (no jump) and is a no-op when
  not frozen (no revision bump).
- A 2 h freeze drops future `time_check` and expired `news` rows, keeps every
  song/liner/commercial, bumps the revision once, and the dropped one-shots
  are spent (not `fresh`). A drop that leaves song-after-song inserts a
  liner/station ID; with no voice inventory the songs stay adjacent and
  nothing crashes.
- A ready request submitted during a freeze is spliced into the frozen window
  and is the next song slot after thaw; freeze/thaw with nothing dropped
  leaves the seeded picks identical.

## 16. Definition of done (Phase 1)

- PLAY is a user click, then endless audio.
- **24 simulated hours** pass all §15 assertions.
- **60 consecutive real minutes** (real backends) with no audible gap and no
  dead air, verified by listening and by the client gap log.
- Consistent loudness across songs and voice (no volume riding).
- Station recovers without silence when any single backend is taken offline.

## 17. Roadmap

**Phase 1 — this build**
Random selector, inventory producers, song + voice pipelines, QC and
normalization, seed script, fakes and simulation tests, minimal UI.

**Phase 2 — richer**
- `ClockSelector`: hour clock with hard news posts at :00/:30 and backtiming
  (fill to the post using liner length buckets). News starts at :45/:15, ready
  by :55/:25; if late, re-air the previous bulletin with a recap intro.
- Music beds pre-mixed under voice spots (short instrumental loops from
  MiniMax, mixed offline at render time).
- Continuity step proposing station bible additions.
- A larger news model on the 5090.
- (Now-playing metadata was pulled forward into Phase 1, §9.1 — program
  `title`/`artist` and the audio-clock-driven song label. The multi-listener
  wall-clock timeline remains Phase 3.)

**Phase 3 — production**
- Multi-listener shared timeline (wall-clock program, drift reconciliation).
- Persistent station state, crash recovery, resume.
- Library pruning policy.
- True streaming transport, only if sequential playback proves limiting.
